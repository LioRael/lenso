# Harness Plugin Authoring Simplification Plans

Generated by the `improve` and `domain-modeling` skills on 2026-08-27. These
plans replace the earlier control-plane-first roadmap. The first user problem
is not Store, Receipt, Controller, or Supervisor visibility. It is that one
Harness extension author must first become a Lenso Module author and then wrap
the same behavior in a second Plugin identity, manifest, release, and instance
model.

The target is deliberately scoped by persona:

- a **Harness Plugin author** creates, develops, checks, packages, and tests one
  Plugin without authoring or naming a Module;
- a **Lenso App owner** selects required embedded Plugins and optional bundled
  or installed Plugins through the same model;
- the runtime may temporarily lower a Plugin into compatibility-era internal
  `Module*` values, but that lowering is generated and absent from every author,
  App-owner, and operator interface;
- V1 has exactly one executable entry per Plugin Release. Multi-entry Plugins,
  Plugin Features, and publisher-authored binding templates remain deferred.

Each executor must read the selected plan completely, create the named
Worktrunk worktree from the recorded `origin/main` baseline, run every
verification gate, and stop on the listed escape conditions. These plans do
not authorize publishing packages, opening pull requests, merging, or creating
remote repositories.

## Dependency and release order

```text
lenso architecture decision
  -> lenso-runtime-rust source-derived Plugin contract
    -> publish and verify Runtime crates
      -> lenso-cli unified Plugin workflow
        -> publish and verify CLI
          -> lenso-agent-harness migration
            -> independent clean-room proof
```

- Plan 001 fixed the first Harness persona. ADR 0069 now supersedes its decision
  to retain Module as a separate public model; immutable execution, Capability
  binding, and above-Kernel Plugin governance remain intact.
- Plan 002 must prove a non-executing descriptor transport before a public
  authoring interface is released. A runtime `describe()` call is not packaging
  authority.
- **Runtime release checkpoint after Plan 002**: with explicit operator
  approval, deliver the Runtime PR, let repository automation publish the
  affected exact crate versions, and verify crates.io plus source tags before
  Plan 003 begins. Without approval, stop with Plan 003 blocked.
- Plan 003 consumes published Runtime crates rather than Git revisions. A
  local workspace pass is not release evidence.
- **CLI release checkpoint after Plan 003**: with explicit operator approval,
  deliver the CLI PR, let Cargo/npm Trusted Publishing complete, and verify the
  exact public artifacts before Plan 004 begins. Without approval, stop with
  Plan 004 blocked.
- Plan 004 consumes a published CLI/package contract and keeps the Kernel
  unchanged. Harness policy may constrain the one generated Plugin entry, but
  may not require the publisher to restate internal Module facts.
- Plan 005 independently re-verifies the checkpoint releases and performs the
  product proof. Any follow-up compatibility-removal release still requires
  explicit operator approval at each repository.
- Plan 006 gives embedded Host behavior a Plugin distribution mode, replaces
  App Definitions with Plugin Roots, and deletes the hidden Module and central
  composition compatibility paths after first-party migration.

## Canonical acceptance workflow

The roadmap is complete only when a new repository can execute this path:

```text
lenso plugin new uppercase
  -> edit Plugin source
  -> lenso plugin dev
  -> lenso plugin check
  -> lenso plugin pack
  -> harness plugins add <bundle>
  -> run the contributed Tool
  -> edit and repack a new version
  -> harness plugins add <new bundle>
  -> run the new version
  -> harness plugins remove <id>
  -> run the base App successfully
```

The authored repository must not contain `#[module]`, `defineModule`, a Module
Descriptor, a `module_contributions` array, a Plugin Manifest template, a Plan,
or a second identity/version/configuration declaration.

## Findings considered and rejected

- **Hide Module only in documentation** — rejected. Today authors compile
  `#[module]`, receive Module diagnostics, and create a Plugin Manifest later;
  wording alone cannot internalize that interface.
- **Keep Module public because embedded behavior is not installed** — rejected
  by ADR 0069. Installability is a distribution mode, not a different behavior
  identity. Private runtime lowering may migrate incrementally.
- **Keep `Plugin` as only a marketing alias for Module** — rejected. It leaves
  two command families and the packaging handoff intact.
- **Require a separate `plugin verify` author step** — rejected. `pack` must
  validate the exact output it creates and Harness `plugins add` must validate
  untrusted input again. A third command adds no authority and misleadingly
  sounds like certification.
- **Support multi-Module or data-only Plugins in V1** — rejected until an
  independent user needs them. The existing generic schema is research, not a
  required first-party contract.
- **Design Bun, QuickJS, Process, native dylib, and Wasm Plugin authoring at
  once** — rejected. The first public tracer is one constrained Rust-authored
  Wasm Component Tool Plugin. Other execution classes join the same Plugin
  interface only when each has an executable tracer.
- **Remove Store, Receipt, Controller, Supervisor, or Generation first** —
  rejected as the primary simplification. Their interfaces should later be
  deepened, but doing so does not repair the dual author identity.
- **Move Plugin discovery into Kernel** — rejected. Kernel continues to execute
  one immutable resolved Plan with no package acquisition or mutable registry.
