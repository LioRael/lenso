# Events on Cloudflare Workers / D1

`@lenso/events/d1` supplies an asynchronous adapter over the existing Events Store
operations. It accepts a borrowed D1 binding (or D1 session); no database is opened,
closed, migrated or queried at module import or store construction. It contains no
Bun/SQLite native import and needs no runtime npm dependency.

```ts
import { createD1EventStore, initializeD1Events } from "@lenso/events/d1";

// Explicit setup/migration job, outside normal request handling:
await initializeD1Events(env.DB);

// Inside a Worker request/scheduled handler:
const store = createD1EventStore(env.DB);
await store.register("receipt-v1", "order.created");
await store.publish({ id: "order:42:created", topic: "order.created", payload: { orderId: 42 } });
const delivery = await store.claim(["receipt-v1"], 30_000);
if (delivery) {
  try {
    await destination.send(delivery.event.payload, { idempotencyKey: delivery.idempotencyKey });
  } catch {
    await store.retry(delivery, 1_000);
    throw new Error("Delivery failed; retry scheduled if the lease was still owned");
  }
  const confirmed = await store.acknowledge(delivery);
  // false means expired, cancelled or superseded: never report confirmed delivery.
}
```

`env` and `destination` belong to the application; publication/cancellation require
its authorization. Use an asynchronous Events service when dispatching handlers
through a service: the original synchronous SQLite `createEvents` does not accept
this store. All adapter operations must be awaited. The shared async service and
package export are integrated separately by the PG/Events integration owner.

## Transaction and recovery semantics

- `initializeD1Events` runs schema setup in one D1 batch. Initialization is explicit
  and idempotent. Request methods do not run DDL.
- Publish inserts the event, snapshots active subscribers, and reads its canonical
  identity in one `D1Database.batch()`. D1 rolls the full batch back if any statement
  fails. `changes()` guards the fanout with the preceding INSERT result. An identical
  producer retry returns `{ created: false }` and never backfills late subscribers.
  Conflicting ID/topic/payload rejects without modifying the existing publication.
- Claim is a single `UPDATE … RETURNING` with eligibility selection inside the same
  SQL statement. It increments attempts and replaces the random token atomically.
  Independent Workers cannot both acquire an unexpired delivery.
- Acknowledge/retry match event, subscription, processing state, token and unexpired
  lease. Cancellation atomically deactivates the subscription and cancels unfinished
  deliveries. Previously delivered records remain delivered.
- Production time is sampled by D1 inside SQL, after queueing, so Worker clock skew
  and request latency do not extend stale claims. `now` is a deterministic test hook;
  overriding it in production forfeits the database-clock guarantee.
- A failed/uncertain claim is recovered after its lease expires. Publication can be
  retried with the same event ID. Storage failures reject to the caller; do not
  blindly retry claim/settlement calls assuming the first attempt did not commit.
- This is at-least-once delivery. Use the stable event/subscription idempotency key
  at the destination. There is no automatic renewal, timer, dead-letter policy,
  retention/pruning, background dispatcher or external exactly-once guarantee.

## Platform boundaries

D1 supports transactional batches, not interactive JavaScript transactions.
Business writes and this adapter's `publish()` cannot be enclosed in one external
D1 transaction: this adapter does not expose prepared publication statements or
claim atomicity with separate business writes. Use an application-specific outbox
when that atomicity is required. SQLite's nested transaction API is unchanged.

The D1 binding executes queries on the primary by default. For read replication,
use the same session/bookmark consistently if status reads must observe earlier
writes; an unconstrained new session can read older status. Mutations remain
fenced by the database. Consult [D1 batch documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch).

D1 query/row/database limits and Worker resource budgets still apply. Large fanout
can exceed a D1 query budget; the batch rejects and rolls back rather than publishing
only part of the subscriber snapshot. The 1 MiB JSON payload cap matches the existing
Store contract, but platform row limits also include ID/topic and database overhead.
No remote performance, deployment, read-replica topology, quota or failover claim
is inferred from local acceptance.

## Local acceptance

From the repository root after the normal frozen dependency preparation:

```sh
# A task-owned tools directory; no root dependency or lock changes.
npm install --prefix /tmp/lenso-d1-tools --no-audit --no-fund \
  miniflare@4.20260730.0 esbuild@0.28.2 @cloudflare/workers-types@5.20261016.1
LENSO_D1_TOOLING=/tmp/lenso-d1-tools node packages/events/test-d1/run.mjs
```

This runs real workerd and local D1, not a mocked SQL connection. It verifies
Cloudflare binding/session type compatibility, transaction rollback with failing
SQLite triggers, deduplication, isolated subscriptions, competing claims, fencing,
retry delay, cancellation, storage rejection, production clock, 16 independent
request claimers, and persisted recovery after destroying/recreating the runtime.
It removes its temporary database in `finally`, never uses a user database or
Cloudflare account, and requires permission to bind local loopback ports. The
pinned runtime supports compatibility date `2026-07-30`; this date is intentionally
kept within the tested runtime's capability rather than claiming untested APIs.
