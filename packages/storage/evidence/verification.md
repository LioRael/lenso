## Before / after

`head-before.txt` runs the added HEAD regression tests against the original Fetch implementation: GET correctly denies the metadata-only user, but HEAD returns 200 instead of 403; the old HEAD path also never acquires/releases the authorized read stream.

The fix uses the same `files.read` authorization and object snapshot for GET and HEAD. HEAD immediately cancels the returned stream and has a null response body. Existing error redaction/status mapping remains in use. HEAD now consults storage, so provider failures and ETag mismatches are observable rather than returning stale database download headers.

`storage-after.txt`: **42 passed, 0 failed, 299 assertions**, scoped to `fetch`, `files`, `local` and `stream`. The two new regressions pass, including zero body pulls and cancellation on HEAD. Existing ambiguous DB commit, upload compensation, retriable deletion and local snapshot tests also pass.

`file-recovery.json` is generated by the executable example using built package exports. It asserts the following sequence against a temporary real SQLite file and dedicated local object directory, then closes the app and removes the temporary data:

1. No file table before explicitly executing the existing SQLite migration.
2. Upload returns 201; typed `db.query.files.findFirst` sees ready state and 18 bytes.
3. A throwing native Drizzle transaction rolls back its attempted filename change.
4. Metadata remains visible while GET/HEAD both return 403 without reaching the provider.
5. Authorized HEAD returns 200; an injected transient GET failure returns sanitized 502; retry returns 200 with the original bytes and unchanged ready record.
6. Changing the application permission rejects subsequent GET and HEAD requests.
7. A 65-byte upload against a 64-byte limit returns 413, persists failed state and leaves no object.
8. Ready-only sorted queries return two distinct one-row pages, then an empty page.
9. Delete and retry return 204, retain the tombstone and leave no stored payload.

The one transient provider failure is deliberately injected. Successful byte storage, read, compensation and deletion use the real local adapter. This is an in-process Fetch application flow with no network listener; it does not exercise a live browser, S3, R2, D1 or PostgreSQL service.
